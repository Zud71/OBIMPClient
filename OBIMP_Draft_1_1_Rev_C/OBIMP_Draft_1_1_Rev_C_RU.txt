OBIMP (Open Binary Instant Messaging Protocol) - Открытый бинарный протокол обмена мгновенными сообщениями
Черновик 1.1, Редакция C.

Содержание:
1. Основная информация
2. Общие типы BEX
3. Последовательности пакетов OBIMP
4. Дополнительные UUID картинок статусов
5. Коды стран и языков

**********************************************************************************
1. Основная информация

Общая информация:
OBIMP - это бинарный сетевой протокол, который передается в сетевом порядке байт (NBO) через TCP.
Этот протокол был разработан для сервисов обмена мгновенными сообщениями. Основная идея заключалась в создании открытого, простого, безопасного и расширяемого бинарного протокола обмена мгновенными сообщениями. OBIMP подразумевает структурированный обмен данными между сервером и клиентами с использованием правил, определенных в этом документе. Каждый протокольный данные начинаются с заголовка OBIMP. Заголовок содержит управляющие значения и специальный тип команды и подтип, которые называются типом и подтипом бинарного расширения (BEX). Все строки, которые должны передаваться внутри пакета OBIMP, должны быть закодированы в кодировку UTF-8, включая имена учетных записей.

Серверы и порты:
Для идентификации соединения OBIMP рекомендуется использовать следующие номера портов на сервере, и эти порты должны быть портами по умолчанию в клиентских программах:

7023 - Номер TCP порта для клиентских соединений
7024 - Номер TCP порта для административных соединений
7025 - Номер TCP порта для прямых/прокси клиентских соединений передачи файлов

7033 - Номер TCP порта для защищенных клиентских соединений через TLS/SSL
7034 - Номер TCP порта для защищенных административных соединений через TLS/SSL
7035 - Номер TCP порта для защищенных прямых/прокси клиентских соединений передачи файлов через TLS/SSL

Типы данных протокола:
Byte, Bool - беззнаковый 1 байт
Word - беззнаковый 2 байта
LongWord - беззнаковый 4 байта
QuadWord - беззнаковый 8 байт
DateTime - знаковый 8 байт, 64-битное дата-время Unix
OctaWord - беззнаковый 16 байт
UUID - беззнаковый 16 байт, Универсальный Уникальный Идентификатор
BLK - массив байт, переменная длина
UTF8 - строка в кодировке UTF-8, переменная длина

Значения даты-времени, которые отправляет сервер, находятся в UTC, исключая значения дня рождения.

Структура заголовка OBIMP (заголовок всегда имеет длину 17 байт):
- Byte: каждая команда сервера/клиента начинается с байта 0x23 - "#";
- LongWord: последовательность, от 0 до 0xFFFFFFFF, первый пакет всегда должен начинаться с 0;
- Word: тип BEX;
- Word: подтип BEX;
- LongWord: идентификатор запроса, используется для маркировки клиентских запросов для их связи с ответами сервера;
- LongWord: длина следующих данных;

Все последующие данные основаны на wTLD (широкий тип-длина-данные) в соответствии с его типом и подтипом BEX.
Типы wTLD уникальны только внутри одного BEX. Не может быть двух или более wTLD с одинаковым типом в одном BEX.

wTLD может содержать один или несколько встроенных sTLD (короткий тип-длина-данные) для описания данных, которые не предполагаются слишком длинными. Для правильной идентификации sTLD все sTLD должны использоваться строго внутри документированных частей данной спецификации.

wTLD может содержать один или несколько встроенных wTLD.

wTLD/sTLD может не иметь данных, это называется пустой wTLD/sTLD, в этом случае длина будет равна нулю.

Структура wTLD:
- Тип: LongWord
- Длина: LongWord
- Данные: данные с указанной длиной

Структура sTLD:
- Тип: Word
- Длина: Word
- Данные: данные с указанной длиной

Обозначение типов BEX в этом документе и ограничения:
Если BEX должен быть отправлен клиентом, он будет помечен как "CLI" внутри определения BEX.
Если BEX должен быть отправлен сервером, он будет помечен как "SRV" внутри определения BEX.
Если один и тот же BEX может быть отправлен клиентом и сервером, он будет помечен как "CLI_SRV" внутри определения BEX.

Поскольку максимальный размер данных BEX может составлять 4 ГБ, и в настоящее время это слишком большой объем данных для одного пакета BEX, существуют клиентские ограничения BEX, и они зависят от конфигурации программного обеспечения сервера OBIMP. По умолчанию каждый клиентский BEX не может быть больше, чем OBIMP_BEX_MAX_DATA_LEN, включая все wTLD внутри BEX, иначе сервер отключит такого клиента. Сервер не имеет ограничений на размер данных BEX для серверных BEX.

OBIMP_BEX_MAX_DATA_LEN = 0x00020000

**********************************************************************************
2. Общие типы BEX

Общие типы BEX передаются между клиентами OBIMP и сервером для сервисов обмена мгновенными сообщениями, включая процессы входа в систему и регистрации учетных записей.

Доступные общие типы BEX:
0x0001, Общий. (OBIMP_BEX_COM)
0x0002, Список контактов. (OBIMP_BEX_CL)
0x0003, Присутствие. (OBIMP_BEX_PRES)
0x0004, Обмен мгновенными сообщениями. (OBIMP_BEX_IM)
0x0005, Каталог пользователей. (OBIMP_BEX_UD)
0x0006, Аватары пользователей. (OBIMP_BEX_UA)
0x0007, Передача файлов. (OBIMP_BEX_FT)
0x0008, Транспорты. (OBIMP_BEX_TP)

=====================================================
BEX 0x0001, Общий. (OBIMP_BEX_COM)
=====================================================
Подтип: 0x0001. (OBIMP_BEX_COM_CLI_HELLO)
Клиент должен сначала инициировать последовательность входа.
Если клиент уже прошел последовательность входа во время установления соединения и получил уникальную серверную cookie, то он должен включить wTLD 0x0002 с cookie. Если cookie верна, то сервер ответит с OBIMP_BEX_COM_LOGIN_REPLY.
Если клиент собирается зарегистрировать новую учетную запись, то он должен добавить только один пустой wTLD 0x0003.

Доступные сценарии запроса:

Запрос:
wTLD 0x0001: UTF8, имя учетной записи
Опционально:
wTLD 0x0002: BLK, уникальная серверная cookie

Запрос:
wTLD 0x0003: пустой, попытка регистрации новой учетной записи
------------------------------------------------------------------------------------------------
Подтип: 0x0002. (OBIMP_BEX_COM_SRV_HELLO)
Если учетная запись действительна, то сервер отправит wTLD 0x0002 с ключом сервера, иначе он отправит wTLD 0x0001 с кодом ошибки приветствия. Вместо отправки ключа сервера, сервер может перенаправить на другой сервер OBIMP, используя wTLD 0x0003 и wTLD 0x0004. Если клиент был перенаправлен, то последовательность входа начнется сначала.
Если клиент запросил регистрацию новой учетной записи, то сервер ответит с wTLD 0x0005. Если в конфигурации сервера доступен URL регистрации, то сервер добавит wTLD 0x0006, где пользователь может зарегистрировать новую учетную запись через веб.
Только для целей совместимости с существующими базами данных пользователей была добавлена аутентификация открытым текстом. Если сервер поддерживает только аутентификацию открытым текстом, он должен отправить только wTLD 0x0007. Этот тип аутентификации не рекомендуется.

Доступные ответы:

Ответ:
wTLD 0x0001: Word, ошибка приветствия (HELLO_ERROR_CODE)

Ответ:
wTLD 0x0002: BLK, ключ сервера для генерации одноразового MD5 хеша пароля
Опционально:
wTLD 0x0008: LongWord, рекомендация минимальной версии microOBIMP SDK

Ответ:
wTLD 0x0003: UTF8, перенаправление, новый хост/ip сервера
wTLD 0x0004: LongWord, перенаправление, новый номер порта сервера

Ответ:
wTLD 0x0005: Bool, если значение True, то регистрация включена
Опционально:
wTLD 0x0006: UTF8, URL регистрации

Ответ:
wTLD 0x0007: пустой, сервер требует аутентификацию паролем открытым текстом

Коды ошибок приветствия:
HELLO_ERROR_ACCOUNT_INVALID = 0x0001
HELLO_ERROR_SERVICE_TEMP_UNAVAILABLE = 0x0002
HELLO_ERROR_ACCOUNT_BANNED = 0x0003
HELLO_ERROR_WRONG_COOKIE = 0x0004
HELLO_ERROR_TOO_MANY_CLIENTS = 0x0005
HELLO_ERROR_INVALID_LOGIN = 0x0006
------------------------------------------------------------------------------------------------
Подтип: 0x0003. (OBIMP_BEX_COM_CLI_LOGIN)
Если сервер ответил ключом сервера, то клиент должен сгенерировать специальный MD5 хеш и отправить его на сервер.
Если сервер запросил аутентификацию паролем открытым текстом, то клиент должен отправить пароль открытым текстом.

Запрос:
wTLD 0x0001: UTF8, имя учетной записи
wTLD 0x0002: OctaWord, одноразовый сгенерированный MD5 хеш (см. ниже, как его сгенерировать)

Запрос:
wTLD 0x0001: UTF8, имя учетной записи
wTLD 0x0003: BLK, пароль в кодировке Base64 из UTF-8

Одноразовый MD5 хеш генерируется с использованием следующей формулы:
MD5( MD5( UTF8Encode( LowerCase(Account) ) + "OBIMPSALT" + UTF8Encode(Password) ) + ServerKey )
Поскольку имя учетной записи и пароль являются Unicode, кодировка UTF-8 используется перед генерацией MD5 хеша, чтобы сделать его более универсальным и независимым от платформы.
Обратите внимание, что LowerCase должен поддерживать "преобразование в нижний регистр" Unicode.
------------------------------------------------------------------------------------------------
Подтип: 0x0004. (OBIMP_BEX_COM_SRV_LOGIN_REPLY)
Если учетная запись и MD5 хеш совпали, то сервер отправит wTLD 0x0002 с поддерживаемыми BEX, wTLD 0x0003 с максимальной длиной данных клиентских BEX и wTLD 0x0008 с версиями BEX, иначе он отправит wTLD 0x0001 с кодом ошибки входа.
Если учетная запись и MD5 хеш совпали, и текущий сервер предназначен только для аутентификации, то он ответит уникальной cookie и с адресом и портом главного сервера, к которому клиент должен подключиться.

Доступные ответы:

Ответ:
wTLD 0x0001: Word, ошибка входа (LOGIN_ERROR_CODE)

Опционально:
wTLD 0x0007: UTF8, URL напоминания пароля, если код неверного пароля

Ответ:
wTLD 0x0002: массив Word, поддерживаемые сервером BEX
(пары Word, первый Word - тип BEX, второй Word - максимальный подтип BEX)

wTLD 0x0003: LongWord, максимальная длина данных клиентских BEX

wTLD 0x0008: массив QuadWord, версии BEX
(первый Word - тип BEX, второй Word - ID разработчика, третий Word - основная версия типа BEX, четвертый Word - минорная версия типа BEX)

Ответ:
wTLD 0x0004: UTF8, новый хост/ip сервера
wTLD 0x0005: LongWord, новый номер порта сервера
wTLD 0x0006: BLK, уникальная серверная cookie

Коды ошибок входа:
LOGIN_ERROR_ACCOUNT_INVALID = 0x0001
LOGIN_ERROR_SERVICE_TEMP_UNAVAILABLE = 0x0002
LOGIN_ERROR_ACCOUNT_BANNED = 0x0003
LOGIN_ERROR_WRONG_PASSWORD = 0x0004
LOGIN_ERROR_INVALID_LOGIN = 0x0005
------------------------------------------------------------------------------------------------
Подтип: 0x0005. (OBIMP_BEX_COM_SRV_BYE)
Сервер может закрыть соединение по какой-либо причине. Он отправит wTLD 0x0001 с кодом причины прощания и после отправки немедленно закроет соединение.

wTLD 0x0001: Word, код причины прощания (BYE_REASON_CODE)

Коды причин прощания:
BYE_REASON_SRV_SHUTDOWN = 0x0001
BYE_REASON_CLI_NEW_LOGIN = 0x0002
BYE_REASON_ACCOUNT_KICKED = 0x0003
BYE_REASON_INCORRECT_SEQ = 0x0004
BYE_REASON_INCORRECT_BEX_TYPE = 0x0005
BYE_REASON_INCORRECT_BEX_SUB = 0x0006
BYE_REASON_INCORRECT_BEX_STEP = 0x0007
BYE_REASON_TIMEOUT = 0x0008
BYE_REASON_INCORRECT_WTLD = 0x0009
BYE_REASON_NOT_ALLOWED = 0x000A
BYE_REASON_FLOODING = 0x000B
------------------------------------------------------------------------------------------------
Подтип: 0x0006. (OBIMP_BEX_COM_CLI_SRV_KEEPALIVE_PING)
Сервер и клиент могут отправлять друг другу проверки активности, чтобы проверить, что соединение не разорвано.
Нет wTLD.

Сервер.
Сервер может отправлять этот BEX каждые n минут, если соединение простаивает. Если сервер не получит ответный BEX pong от клиента в течение следующих n минут, сервер закроет соединение.

Клиент.
Клиент может отправить этот BEX в любое время после последовательности входа, если необходимо. Если ответный BEX pong от сервера не был получен в течение времени, определенного разработчиком клиента, клиент должен закрыть соединение.
------------------------------------------------------------------------------------------------
Подтип: 0x0007. (OBIMP_BEX_COM_CLI_SRV_KEEPALIVE_PONG)
После получения ping BEX, клиент/сервер должен ответить этим BEX, чтобы уведомить, что соединение не разорвано.
Нет wTLD.
------------------------------------------------------------------------------------------------
Подтип: 0x0008. (OBIMP_BEX_COM_CLI_REGISTER)
Клиент пытается зарегистрировать новую учетную запись. Не рекомендуется включать регистрацию через протокол, если вы собираетесь сделать общедоступный IM сервер. Если регистрация отключена, клиент может зарегистрировать новую учетную запись только путем добавления wTLD 0x0004 с текущим административным ключом сервера. Это полезно, если регистрация для клиентов отключена и используется только веб-форма или административная программа для регистрации.

wTLD 0x0001: UTF8, имя учетной записи (максимальная длина в кодировке UTF-8 зависит от настроек сервера)
wTLD 0x0002: UTF8, пароль (максимальная длина в кодировке UTF-8 равна 1024)

Опционально:
wTLD 0x0003: UTF8, защищенный email (максимальная длина в кодировке UTF-8 равна 1024)
wTLD 0x0004: BLK, текущий административный ключ сервера
------------------------------------------------------------------------------------------------
Подтип: 0x0009. (OBIMP_BEX_COM_SRV_REGISTER_REPLY)
Это ответ сервера на попытку регистрации.
Если сервер ответил с REG_RES_BAD_ACCOUNT_NAME, то он включит опциональные wTLD с условиями регистрации.

wTLD 0x0001: Word, код результата регистрации (см. ниже)

Опционально:
wTLD 0x0002: UTF8, разрешенные символы в имени учетной записи для регистрации
wTLD 0x0003: UTF8, запрещенные первые символы в имени учетной записи для регистрации
wTLD 0x0004: UTF8, запрещенные последние символы в имени учетной записи для регистрации
wTLD 0x0005: LongWord, минимальная длина имени учетной записи для регистрации

Коды результатов регистрации:
REG_RES_SUCCESS = 0x0000
REG_RES_DISABLED = 0x0001
REG_RES_ACCOUNT_EXISTS = 0x0002
REG_RES_BAD_ACCOUNT_NAME = 0x0003
REG_RES_BAD_REQUEST = 0x0004
REG_RES_BAD_SERVER_KEY = 0x0005
REG_RES_SERVICE_TEMP_UNAVAILABLE = 0x0006
REG_RES_EMAIL_REQUIRED = 0x0007
=====================================================
BEX 0x0002, Список контактов. (OBIMP_BEX_CL)
=====================================================
Подтип: 0x0001. (OBIMP_BEX_CL_CLI_PARAMS)
Клиент должен запросить параметры и ограничения списка контактов, чтобы уведомить пользователя о превышении любого лимита.
Нет wTLD.
------------------------------------------------------------------------------------------------
Подтип: 0x0002. (OBIMP_BEX_CL_SRV_PARAMS_REPLY)
Параметры и ограничения списка контактов:

wTLD 0x0001: LongWord, максимальное количество групп
wTLD 0x0002: LongWord, максимальная длина имени группы в кодировке UTF-8
wTLD 0x0003: LongWord, максимальное количество контактов во всем списке контактов
wTLD 0x0004: LongWord, максимальная длина имени учетной записи в кодировке UTF-8
wTLD 0x0005: LongWord, максимальная длина имени контакта/дружественного имени транспорта в кодировке UTF-8
wTLD 0x0006: LongWord, максимальная длина причины/отзыва авторизации в кодировке UTF-8
wTLD 0x0007: LongWord, максимальное количество пользовательских/разработческих sTLD в одном элементе
wTLD 0x0008: LongWord, максимальная длина пользовательского/разработческого sTLD
wTLD 0x0009: LongWord, количество автономных авторизационных сообщений (запросов, ответов, отзывов), ожидающих запроса клиента
wTLD 0x000A: Bool, если True, то сервер автоматически удалит флаг авторизации после добавления контакта
wTLD 0x000B: LongWord, максимальное количество заметок
wTLD 0x000C: LongWord, максимальная длина имени заметки в кодировке UTF-8
wTLD 0x000D: LongWord, максимальная длина текста заметки в кодировке UTF-8
------------------------------------------------------------------------------------------------
Подтип: 0x0003. (OBIMP_BEX_CL_CLI_REQUEST)
Клиент может запросить список контактов на стороне сервера в любое время во время сеанса.
Нет wTLD.
------------------------------------------------------------------------------------------------
Подтип: 0x0004. (OBIMP_BEX_CL_SRV_REPLY)
Данные списка контактов на стороне сервера будут возвращены в wTLD 0x0001.

wTLD 0x0001: BLK, данные списка контактов (см. ниже, как их разобрать)

Типы элементов списка контактов:
CL_ITEM_TYPE_GROUP = 0x0001
CL_ITEM_TYPE_CONTACT = 0x0002
CL_ITEM_TYPE_TRANSPORT = 0x0003
CL_ITEM_TYPE_NOTE = 0x0004

Разбор данных списка контактов.
Он состоит из двух частей:
1. LongWord, количество элементов в списке контактов.
2. Массив элементов списка контактов.

Структура элемента списка контактов универсальна для любого типа элемента и состоит из:
Word, Тип элемента
LongWord, ID элемента
LongWord, ID группы
LongWord, длина следующих sTLD в соответствии с типом элемента:

для Групп:
sTLD 0x0001: UTF8, имя группы

для Контактов:
sTLD 0x0002: UTF8, имя учетной записи
sTLD 0x0003: UTF8, имя контакта
sTLD 0x0004: Byte, тип приватности
sTLD 0x0005: пустой, флаг авторизации (может быть удален только сервером)
sTLD 0x0006: пустой, флаг общего элемента (может быть добавлен/удален только сервером)

Опционально:
sTLD 0x1001: LongWord, ID элемента транспорта (не может быть удален)

для Транспортов:
sTLD 0x1002: UUID, UUID транспорта
sTLD 0x1003: UTF8, имя учетной записи транспорта
sTLD 0x1004: UTF8, дружественное имя транспорта

для Заметок:
sTLD 0x2001: UTF8, имя заметки
sTLD 0x2002: Byte, тип заметки

Опционально:
sTLD 0x2003: UTF8, текст заметки
sTLD 0x2004: DateTime, дата заметки (UTC)
sTLD 0x2005: OctaWord, MD5 хеш картинки заметки

Каждый элемент имеет уникальный ID элемента, каждый элемент имеет ID группы. Элемент группы имеет ID группы родительской группы, если это подгруппа. Если ID группы = 0, то элемент не имеет родительской группы.

Если элемент имеет флаг общего элемента, то это означает, что этот элемент был добавлен и может быть удален только администратором.

Каждый элемент может иметь свои собственные sTLD, указанные пользователем/разработчиком, для любых нужд, но они должны начинаться с sTLD 0x8000 и должны соответствовать ограничениям sTLD.

Типы приватности контактов:
CL_PRIV_TYPE_NONE = 0x00
CL_PRIV_TYPE_VISIBLE_LIST = 0x01
CL_PRIV_TYPE_INVISIBLE_LIST = 0x02
CL_PRIV_TYPE_IGNORE_LIST = 0x03
CL_PRIV_TYPE_IGNORE_NOT_IN_LIST = 0x04

Когда клиент добавляет или изменяет контакт с типом приватности CL_PRIV_TYPE_IGNORE_NOT_IN_LIST, ID группы всегда должен быть 0, иначе сервер вернет ошибку. Это потому, что такие контакты не должны находиться в списке контактов.

Типы заметок:
CL_NOTE_TYPE_TEXT = 0x00
CL_NOTE_TYPE_COMMAND = 0x01
CL_NOTE_TYPE_LINK = 0x02
CL_NOTE_TYPE_EMAIL = 0x03
CL_NOTE_TYPE_PHONE = 0x04
------------------------------------------------------------------------------------------------
Подтип: 0x0005. (OBIMP_BEX_CL_CLI_VERIFY)
Если у клиента есть локальная копия списка контактов, он может проверить ее контрольную сумму с копией списка контактов на стороне сервера вместо запроса полного списка контактов с сервера.
Чтобы использовать этот BEX, клиент должен сохранить локальную копию списка контактов в формате сервера и проверить MD5 данных списка контактов, описанных выше, с MD5 контрольной суммой, полученной от сервера на этот запрос.

Нет wTLD.
------------------------------------------------------------------------------------------------
Подтип: 0x0006. (OBIMP_BEX_CL_SRV_VERIFY_REPLY)
Сервер ответит текущей MD5 контрольной суммой списка контактов на стороне сервера, чтобы клиент решил, запросить список контактов с сервера или локальная копия актуальна.

wTLD 0x0001: OctaWord, MD5 контрольная сумма BLOB-объекта списка контактов на стороне сервера
------------------------------------------------------------------------------------------------
Подтип: 0x0007. (OBIMP_BEX_CL_CLI_ADD_ITEM)
Клиент добавляет элемент в список контактов на стороне сервера. Если клиент добавляет новый элемент контакта, то он должен добавить флаг авторизации, иначе сервер вернет ошибку неверного запроса.

wTLD 0x0001: Word, Тип элемента списка контактов
wTLD 0x0002: LongWord, ID родительской группы добавляемого элемента
wTLD 0x0003: массив sTLD, sTLD добавляемого элемента в соответствии с типом элемента
------------------------------------------------------------------------------------------------
Подтип: 0x0008. (OBIMP_BEX_CL_SRV_ADD_ITEM_REPLY)
Сервер ответит wTLD 0x0001 с кодом результата добавления. Если нет ошибки при добавлении нового элемента, сервер добавит wTLD 0x0002 с вновь добавленным ID элемента.

wTLD 0x0001: Word, код результата добавления (ADD_RES_CODE)
wTLD 0x0002: LongWord, вновь добавленный ID элемента

Коды результатов добавления:
ADD_RES_SUCCESS = 0x0000
ADD_RES_ERROR_WRONG_ITEM_TYPE = 0x0001
ADD_RES_ERROR_WRONG_PARENT_GROUP = 0x0002
ADD_RES_ERROR_NAME_LEN_LIMIT = 0x0003
ADD_RES_ERROR_WRONG_NAME = 0x0004
ADD_RES_ERROR_ITEM_ALREADY_EXISTS = 0x0005
ADD_RES_ERROR_ITEM_LIMIT_REACHED = 0x0006
ADD_RES_ERROR_BAD_REQUEST = 0x0007
ADD_RES_ERROR_BAD_ITEM_STLD = 0x0008
ADD_RES_ERROR_NOT_ALLOWED = 0x0009
------------------------------------------------------------------------------------------------
Подтип: 0x0009. (OBIMP_BEX_CL_CLI_DEL_ITEM)
Клиент удаляет элемент из списка контактов на стороне сервера.

wTLD 0x0001: LongWord, ID элемента
------------------------------------------------------------------------------------------------
Подтип: 0x000A. (OBIMP_BEX_CL_SRV_DEL_ITEM_REPLY)
Сервер ответит wTLD 0x0001.

wTLD 0x0001: Word, код результата удаления (DEL_RES_CODE)

Коды результатов удаления:
DEL_RES_SUCCESS = 0x0000
DEL_RES_ERROR_NOT_FOUND = 0x0001
DEL_RES_ERROR_NOT_ALLOWED = 0x0002
DEL_RES_ERROR_GROUP_NOT_EMPTY = 0x0003
------------------------------------------------------------------------------------------------
Подтип: 0x000B. (OBIMP_BEX_CL_CLI_UPD_ITEM)
Клиент обновляет элемент списка контактов на стороне сервера. Клиент может обновить каждое поле элемента, за исключением типа элемента, ID элемента, имени учетной записи, флага авторизации. Клиент должен указать в wTLD 0x0001 ID элемента, который обновляется. Чтобы изменить родительскую группу, клиент должен добавить wTLD 0x0002 с новым ID родительской группы. Чтобы изменить другие данные, клиент должен добавить wTLD 0x0003 с sTLD. wTLD 0x0003 должен включать все sTLD этого элемента, даже если большинство из них не будут изменены, потому что отсутствующие sTLD будут интерпретироваться сервером как то, что клиент собирается их удалить.

Клиент не должен удалять флаг авторизации, если он еще не был удален сервером, или не должен добавлять флаг авторизации, если он уже был удален сервером. В обоих случаях сервер вернет ошибку неверного запроса, если такая ошибка произойдет.

wTLD 0x0001: LongWord, ID элемента
wTLD 0x0002: Новый ID родительской группы (опционально)
wTLD 0x0003: массив sTLD, sTLD элемента в соответствии с типом элемента (опционально)
------------------------------------------------------------------------------------------------
Подтип: 0x000C. (OBIMP_BEX_CL_SRV_UPD_ITEM_REPLY)
Сервер ответит wTLD 0x0001.

wTLD 0x0001: Word, код результата операции обновления (UPD_RES_CODE)

Коды результатов операции обновления:
UPD_RES_SUCCESS = 0x0000
UPD_RES_ERROR_NOT_FOUND = 0x0001
UPD_RES_ERROR_WRONG_PARENT_GROUP = 0x0002
UPD_RES_ERROR_NAME_LEN_LIMIT = 0x0003
UPD_RES_ERROR_WRONG_NAME = 0x0004
UPD_RES_ERROR_ITEM_ALREADY_EXISTS = 0x0005
UPD_RES_ERROR_BAD_REQUEST = 0x0006
UPD_RES_ERROR_BAD_ITEM_STLD = 0x0007
UPD_RES_ERROR_NOT_ALLOWED = 0x0008
------------------------------------------------------------------------------------------------
Подтип: 0x000D. (OBIMP_BEX_CL_CLI_SRV_AUTH_REQUEST)
Каждый новый добавленный контакт в список контактов не будет авторизован. Чтобы получать информацию о присутствии, клиент должен запросить авторизацию у добавленного контакта.
Удаленный пользователь решит разрешить или отклонить этот запрос. Запрос авторизации должен быть отправлен только контакту, который находится в списке контактов клиента и не авторизован, иначе сервер закроет соединение с причиной "не разрешено".

wTLD 0x0001: UTF8, имя учетной записи получателя/отправителя запроса авторизации
wTLD 0x0002: UTF8, причина запроса авторизации

Сервер может добавлять следующие wTLD:
wTLD 0x0003: пустой, флаг автономного авторизационного сообщения
wTLD 0x0004: DateTime, время автономного авторизационного сообщения

Опционально:
wTLD 0x1001: LongWord, ID элемента транспорта
------------------------------------------------------------------------------------------------
Подтип: 0x000E. (OBIMP_BEX_CL_CLI_SRV_AUTH_REPLY)
Ответ удаленного контакта на запрос авторизации.

Если запрос авторизации был разрешен удаленным контактом, то сервер автоматически удалит флаг авторизации для этого контакта в списке контактов на стороне сервера, и клиент будет получать информацию о присутствии этого контакта в соответствии со статусом удаленного контакта. Когда сервер удалит флаг авторизации, он уведомит клиента, отправив OBIMP_BEX_CL_SRV_ITEM_OPER, чтобы внести изменения в локальную копию списка контактов.

Если запрос авторизации был отклонен удаленным контактом, то клиент должен предложить удаление этого контакта или повторную отправку запроса авторизации позже.

wTLD 0x0001: UTF8, имя учетной записи получателя/отправителя ответа авторизации
wTLD 0x0002: Word, код ответа авторизации

Сервер может добавлять следующие wTLD:
wTLD 0x0003: пустой, флаг автономного авторизационного сообщения
wTLD 0x0004: DateTime, время автономного авторизационного сообщения

Опционально:
wTLD 0x1001: LongWord, ID элемента транспорта

Код ответа авторизации:
AUTH_REPLY_GRANTED = 0x0001
AUTH_REPLY_DENIED = 0x0002
------------------------------------------------------------------------------------------------
Подтип: 0x000F. (OBIMP_BEX_CL_CLI_SRV_AUTH_REVOKE)
Контакт может отозвать ранее разрешенную авторизацию.
Когда сервер удалит флаг авторизации, он уведомит клиента, отправив OBIMP_BEX_CL_SRV_ITEM_OPER, чтобы внести изменения в локальную копию списка контактов.
Клиент должен вручную добавить флаг авторизации в свою локальную копию списка контактов, потому что сервер перестанет отправлять информацию о присутствии для этого контакта.

wTLD 0x0001: UTF8, имя учетной записи получателя/отправителя отзыва авторизации
wTLD 0x0002: UTF8, причина отзыва авторизации

Сервер может добавлять следующие wTLD:
wTLD 0x0003: пустой, флаг автономного авторизационного сообщения
wTLD 0x0004: DateTime, время автономного авторизационного сообщения

Опционально:
wTLD 0x1001: LongWord, ID элемента транспорта
------------------------------------------------------------------------------------------------
Подтип: 0x0010. (OBIMP_BEX_CL_CLI_REQ_OFFAUTH)
Используя этот BEX, клиент должен запросить автономные запросы авторизации, ответы и отзывы при каждом входе в систему, если в BEX OBIMP_BEX_CL_SRV_PARAMS_REPLY количество ожидающих автономных авторизационных сообщений больше нуля. Если доступны автономные авторизационные сообщения, сервер отправит запросы авторизации, ответы или отзывы с меткой автономного режима.
Нет wTLD.
------------------------------------------------------------------------------------------------
Подтип: 0x0011. (OBIMP_BEX_CL_SRV_DONE_OFFAUTH)
После того как все автономные авторизационные сообщения были отправлены клиенту с сервера, сервер уведомит клиента о том, что все авторизационные сообщения отправлены клиенту, и они должны быть удалены клиентом.
Нет wTLD.
------------------------------------------------------------------------------------------------
Подтип: 0x0012. (OBIMP_BEX_CL_CLI_DEL_OFFAUTH)
Чтобы удалить все автономные авторизационные сообщения, клиент должен отправить этот BEX. Обычно он должен быть отправлен после получения серверного BEX OBIMP_BEX_CL_SRV_DONE_OFFAUTH.
Нет wTLD.
------------------------------------------------------------------------------------------------
Подтип: 0x0013. (OBIMP_BEX_CL_SRV_ITEM_OPER)
Сервер уведомляет клиента о том, что была операция со списком контактов на стороне сервера с одним элементом. Клиент должен внести изменения в локальный список контактов в соответствии с этой операцией.

wTLD 0x0001: Word, код операции (OPER_CODE)
wTLD 0x0002: Word, Тип элемента списка контактов
wTLD 0x0003: LongWord, ID элемента
wTLD 0x0004: LongWord, ID группы
wTLD 0x0005: массив sTLD, sTLD элемента в соответствии с типом элемента

Коды операций сервера:
OPER_ADD_ITEM = 0x0001
OPER_DEL_ITEM = 0x0002
OPER_UPD_ITEM = 0x0003
------------------------------------------------------------------------------------------------
Подтип: 0x0014. (OBIMP_BEX_CL_SRV_BEGIN_UPDATE)
Сервер может уведомить клиента о том, что будут операции со списком контактов на стороне сервера с одним или несколькими элементами. Клиент должен подготовиться к внесению изменений в локальную копию списка контактов.
После этого BEX клиент получит один или несколько OBIMP_BEX_CL_SRV_ITEM_OPER.
Нет wTLD.
------------------------------------------------------------------------------------------------
Подтип: 0x0015. (OBIMP_BEX_CL_SRV_END_UPDATE)
Сервер уведомляет клиента о том, что операции со списком контактов на стороне сервера завершены.
Нет wTLD.
=====================================================
BEX 0x0003, Присутствие. (OBIMP_BEX_PRES)
=====================================================
Подтип: 0x0001. (OBIMP_BEX_PRES_CLI_PARAMS)
Клиент должен запросить параметры и ограничения информации о присутствии, чтобы уведомить пользователя о превышении любого лимита.
Нет wTLD.
------------------------------------------------------------------------------------------------
Подтип: 0x0002. (OBIMP_BEX_PRES_SRV_PARAMS_REPLY)
Параметры информации о присутствии:

wTLD 0x0001: LongWord, максимальная длина имени статуса в кодировке UTF-8
wTLD 0x0002: LongWord, максимальная длина дополнительной картинки статуса в кодировке UTF-8
wTLD 0x0003: LongWord, максимальная длина имени клиента в кодировке UTF-8
wTLD 0x0004: LongWord, максимальное количество возможностей
wTLD 0x0005: LongWord, требуемые опциональные флаги информации о клиенте (см. ниже)

Требуемые опциональные флаги информации о клиенте:
PRES_REQ_FLAG_HOSTNAME = 0x00000001
------------------------------------------------------------------------------------------------
Подтип: 0x0003. (OBIMP_BEX_PRES_CLI_SET_PRES_INFO)
Прежде чем уведомлять контакты об информации о присутствии клиента, клиент должен установить свои собственные возможности.
Клиент всегда может изменить эту информацию во время сеанса.

wTLD 0x0001: Массив Word, возможности клиента (см. ниже)
wTLD 0x0002: Word, тип клиента (см. ниже)
wTLD 0x0003: UTF8, имя клиента пользователя
wTLD 0x0004: QuadWord, версия клиента пользователя (см. ниже)
wTLD 0x0005: Word, код языка клиента пользователя (можно найти в конце этого документа)

Опционально:
wTLD 0x0006: UTF8, имя операционной системы клиента пользователя (максимальная длина в кодировке UTF-8 равна 128)
wTLD 0x0007: UTF8, дополнительное описание клиента пользователя (максимальная длина в кодировке UTF-8 равна 512)
wTLD 0x0008: LongWord, флаги клиента для информации о присутствии (см. ниже)
wTLD 0x0009: UTF8, имя хоста клиента пользователя (максимальная длина в кодировке UTF-8 равна 255)

Доступные возможности клиента:
CAP_MSGS_UTF8 = 0x0001 - поддержка сообщений в кодировке UTF-8 (требуется для всех клиентов)
CAP_MSGS_RTF = 0x0002 - поддержка сообщений RTF (Rich Text Format) с кодировкой UTF-8
CAP_MSGS_HTML = 0x0003 - поддержка сообщений HTML (HyperText Markup Language) с кодировкой UTF-8
CAP_MSGS_ENCRYPT = 0x0004 - поддержка шифрования
CAP_NOTIFS_TYPING = 0x0005 - поддержка уведомлений о наборе текста
CAP_AVATARS = 0x0006 - поддержка аватаров
CAP_FILE_TRANSFER = 0x0007 - поддержка передачи файлов
CAP_TRANSPORTS = 0x0008 - поддержка транспортов
CAP_NOTIFS_ALARM = 0x0009 - поддержка уведомлений будильника
CAP_NOTIFS_MAIL = 0x000A - поддержка уведомлений о почте

Доступные типы клиентов:
CLIENT_TYPE_USER = 0x0001
CLIENT_TYPE_BOT = 0x0002
CLIENT_TYPE_SERVICE = 0x0003

Версия клиента представлена как 8 байт, где каждые следующие 2 байта означают основную, минорную версию, версию выпуска и номер сборки версии.

Флаги клиента регулируют получение некоторых полей информации о присутствии контактов.
В основном это нужно для целей экономии трафика. Доступные флаги клиента:
PRES_CF_RCV_CLIENT_NAME_AND_VER = 0x00000001
PRES_CF_RCV_OS_INFORMATION = 0x00000002
PRES_CF_RCV_CLIENT_DESCRIPTION = 0x00000004
PRES_CF_RCV_CLIENT_ID_BLK = 0x00000008
------------------------------------------------------------------------------------------------
Подтип: 0x0004. (OBIMP_BEX_PRES_CLI_SET_STATUS)
Клиент устанавливает собственную информацию о присутствии. wTLD 0x0001 всегда должен быть включен в этот BEX.
Опциональный wTLD 0x0002 с именем статуса может быть включен для статусов разработчиков, которые не определены здесь.

Клиент не может использовать wTLD 0x0003 и wTLD 0x0005 в одном BEX (можно использовать только один из этих wTLD). Использование wTLD 0x0005 рекомендуется, если клиент будет использоваться на общедоступных серверах OBIMP. Общие UUID дополнительных картинок статусов доступны в конце этого документа (параграф 5).

wTLD 0x0001: LongWord, значение статуса присутствия (см. ниже)

Опционально:
wTLD 0x0002: UTF8, имя статуса
wTLD 0x0003: LongWord, номер дополнительной картинки статуса
wTLD 0x0004: UTF8, описание дополнительной картинки статуса
wTLD 0x0005: UUID, ID дополнительной картинки статуса

Доступные значения статусов присутствия по умолчанию:
PRES_STATUS_ONLINE = 0x0000
PRES_STATUS_INVISIBLE = 0x0001
PRES_STATUS_INVISIBLE_FOR_ALL = 0x0002
PRES_STATUS_FREE_FOR_CHAT = 0x0003
PRES_STATUS_AT_HOME = 0x0004
PRES_STATUS_AT_WORK = 0x0005
PRES_STATUS_LUNCH = 0x0006
PRES_STATUS_AWAY = 0x0007
PRES_STATUS_NOT_AVAILABLE = 0x0008
PRES_STATUS_OCCUPIED = 0x0009
PRES_STATUS_DO_NOT_DISTURB = 0x000A

Пользователи/разработчики могут добавлять свои собственные значения статусов, начиная с 0x80000000.
PRES_STATUS_DEVELOPER >= 0x80000000
------------------------------------------------------------------------------------------------
Подтип: 0x0005. (OBIMP_BEX_PRES_CLI_ACTIVATE)

wTLD 0x000C: OctaWord, MD5 хеш аватара
wTLD 0x000D: UTF8, IP-адрес клиента
wTLD 0x000E: UUID, ID дополнительной картинки статуса
wTLD 0x000F: UTF8, имя операционной системы клиента пользователя
wTLD 0x0010: UTF8, дополнительное описание клиента пользователя
wTLD 0x0011: Byte, ID пользовательской картинки статуса транспорта
wTLD 0x0012: BLK, массив идентификационных sTLD клиента, определенных транспортом

Подтип: 0x0006. (OBIMP_BEX_IM_CLI_MESSAGE)
Клиент отправляет сообщение. Тип сообщения должен быть выбран с использованием возможностей удаленного клиента. Базовая возможность - сообщение в кодировке UTF-8. Она должна использоваться для отправки сообщений контактам не из списка и онлайн-контактам, которые не поддерживают никакие другие типы сообщений. Если удаленный клиент не имеет возможности поддержки типа сообщения, то такое сообщение даже не будет доставлено удаленному клиенту. Каждое сообщение должно иметь уникальный ID сообщения, и он не должен быть нулевым, иначе сервер закроет соединение. Уникальный ID сообщения генерируется клиентом, и это может быть любой тип счетчика.

Чтобы отправить зашифрованное сообщение, клиент должен добавить wTLD 0x0006, но сначала он должен запросить открытый ключ у удаленного контакта с помощью соответствующего BEX.
Если открытый ключ удаленного контакта получен, то клиент может зашифровать сообщение.
В этом случае wTLD 0x0004 должен быть сгенерирован с использованием следующей формулы:
LongWord Длина зашифрованного сеансового ключа + ЗашифрованныйСеансовыйКлюч +
LongWord Длина зашифрованного сообщения + ЗашифрованноеСообщение

wTLD 0x0002: LongWord, уникальный ID сообщения
wTLD 0x0003: LongWord, тип сообщения (см. ниже)
wTLD 0x0004: BLK, данные сообщения

Управляющие коды передачи файлов:

FT_CONTROL_CODE_DIRECT_FAILED_TRY_REVERSE = 0x0003
FT_CONTROL_CODE_DIRECT_FAILED_TRY_PROXY = 0x0004
FT_CONTROL_CODE_PROXY_FAILED = 0x0005
FT_CONTROL_CODE_READY = 0x0006
------------------------------------------------------------------------------------------------
Подробнее о сценариях соединения передачи файлов:

Прямой/обратный прямой/проксируемый:
В случае, если отправитель указал свой IP-адрес клиента и порт, то должен начаться сценарий прямого соединения.
После принятия передачи файла отправкой ответного сообщения с кодом FT_REPLY_CODE_ACCEPT, получатель должен ждать управляющий код FT_CONTROL_CODE_READY от отправителя и только после получения этого управляющего кода получатель должен попытаться подключиться к отправителю. Если соединение не удается и получатель также указал свой IP-адрес клиента и порт, то получатель должен попросить отправителя, отправив управляющий код FT_CONTROL_CODE_DIRECT_FAILED_TRY_REVERSE, чтобы попробовать обратное соединение.
В этом случае отправитель должен попытаться подключиться к получателю. Если обратное соединение не удается и отправитель указал адрес прокси и порт, то должен начаться сценарий проксируемого соединения.
Отправитель попросит получателя, отправив управляющий код FT_CONTROL_CODE_DIRECT_FAILED_TRY_PROXY, попытаться подключиться к прокси-серверу файлов, и оба клиента должны подключиться к прокси-серверу файлов. Если подключение к прокси не удается на одном из клиентов, то этот клиент должен отправить управляющий код FT_CONTROL_CODE_PROXY_FAILED, и оба клиента должны остановить процесс передачи файлов.

Только проксируемый:
В случае, если отправитель указал только адрес прокси-сервера файлов и порт, то оба клиента должны использовать сценарий проксируемого соединения.
После принятия передачи файла отправкой ответного сообщения с кодом FT_REPLY_CODE_ACCEPT, получатель должен ждать управляющий код FT_CONTROL_CODE_READY от отправителя и только после получения этого управляющего кода получатель должен попытаться подключиться к прокси-серверу файлов. Если подключение к прокси не удается на одном из клиентов, то этот клиент должен отправить управляющий код FT_CONTROL_CODE_PROXY_FAILED, и оба клиента должны остановить процесс передачи файлов.

Только прямой:
В случае, если отправитель указал только IP-адрес клиента и порт, то после принятия передачи файла отправкой ответного сообщения с кодом FT_REPLY_CODE_ACCEPT, получатель должен ждать управляющий код FT_CONTROL_CODE_READY от отправителя и только после получения этого управляющего кода получатель должен попытаться подключиться к отправителю. Если попытка соединения не удалась, то получатель должен отправить управляющий код FT_CONTROL_CODE_DIRECT_FAILED, и оба клиента должны остановить процесс передачи файлов.

Подтип: 0x0001. (OBIMP_BEX_TP_CLI_PARAMS)

Подтип: 0x0002. (OBIMP_BEX_TP_SRV_PARAMS_REPLY)
Параметры транспортов.

Разбор данных доступных транспортов.
Он состоит из двух частей:
1. LongWord, количество доступных элементов транспортов.
2. Элементы транспортов.

Каждый элемент транспорта состоит из:
UUID, уникальный ID транспорта
LongWord, длина следующих sTLD, описывающих транспорт:

sTLD 0x0001: UTF8, полное имя транспорта
sTLD 0x0002: UTF8, короткое имя транспорта
sTLD 0x0003: UTF8, имя идентификаторов учетных записей
sTLD 0x0004: UTF8, хост/IP сервера по умолчанию
sTLD 0x0005: LongWord, номер порта сервера по умолчанию
sTLD 0x0006: Массив LongWord, массив поддерживаемых статусов присутствия OBIMP (исключая статус "онлайн", поддерживаемый по умолчанию)
sTLD 0x0007: Bool, поддерживаются ли дополнительные картинки статуса
sTLD 0x0008: Byte, количество дополнительных картинок статуса
sTLD 0x0009: Bool, поддерживается ли добавление контактов
sTLD 0x000A: Bool, поддерживается ли обновление контактов
sTLD 0x000B: Bool, поддерживается ли удаление контактов
sTLD 0x000C: Bool, поддерживается ли список видимых
sTLD 0x000D: Bool, поддерживается ли список невидимых
sTLD 0x000E: Bool, поддерживается ли список игнорируемых
sTLD 0x000F: Bool, поддерживается ли перемещение в список игнорируемых
sTLD 0x0010: Bool, поддерживаются ли запросы авторизации
sTLD 0x0011: Bool, поддерживаются ли сообщения отзыва авторизации
sTLD 0x0012: Bool, поддерживаются ли подтверждения сообщений
sTLD 0x0013: Bool, поддерживаются ли уведомительные сообщения
sTLD 0x0014: Bool, поддерживаются ли запросы деталей
sTLD 0x0015: Bool, поддерживается ли обновление собственных деталей
sTLD 0x0016: Bool, поддерживается ли поиск в каталоге пользователей
sTLD 0x0017: Bool, поддерживаются ли аватары
sTLD 0x0018: Bool, поддерживается ли обновление собственного аватара
sTLD 0x0019: Bool, поддерживаются ли автономные сообщения
sTLD 0x001A: Bool, поддерживаются ли запросы информации о присутствии
sTLD 0x001B: Bool, поддерживается ли текст причины запроса авторизации
sTLD 0x001C: Bool, поддерживается ли текст причины отзыва авторизации
sTLD 0x001D: Bool, поддерживается ли запрос URL собственного почтового ящика

Следующие sTLD URL ресурсов могут быть добавлены, если доступны картинки транспорта:
sTLD 0x0080: LongWord, текущая версия ресурсов (если изменена, ресурсы должны быть загружены заново)
sTLD 0x0081: UTF8, URL PNG файлов статусов (см. ниже для описания)
sTLD 0x0082: UTF8, URL PNG файлов дополнительных картинок статуса (см. ниже для описания)
sTLD 0x0083: UTF8, URL PNG файлов пользовательских картинок статуса (см. ниже для описания)

Описание значения URL:
Одно значение на строку [доступная высота картинки, URL картинки].
Поскольку клиенты могут поддерживать разные разрешения картинок для лучшего просмотра, в sTLD может быть один URL на строку, но с разным значением высоты, которое может быть выбрано клиентом по предпочтению. Например:
Данные sTLD 0x0081:
16, http://obimp.org/statuses16.png
24, http://obimp.org/statuses24.png
36, http://obimp.org/statuses36.png
48, http://obimp.org/statuses48.png

Индексы статусов в PNG файле статусов должны быть одинаковыми для всех транспортов. Если какой-то статус не поддерживается, то для этого индекса статуса должно остаться пустое место.
Картинки индексов с 1 по 5 в PNG файле не должны быть пустыми.
Доступные индексы PNG файла статусов транспорта OBIMP:
OBIMP_TP_STATUS_INDEX_LOGO = 1
OBIMP_TP_STATUS_INDEX_ONLINE = 2
OBIMP_TP_STATUS_INDEX_OFFLINE = 3
OBIMP_TP_STATUS_INDEX_CONNECTING = 4
OBIMP_TP_STATUS_INDEX_NOT_IN_LIST = 5
OBIMP_TP_STATUS_INDEX_INVISIBLE = 6
OBIMP_TP_STATUS_INDEX_INVISIBLE_FOR_ALL = 7
OBIMP_TP_STATUS_INDEX_AWAY = 8
OBIMP_TP_STATUS_INDEX_NOT_AVAILABLE = 9
OBIMP_TP_STATUS_INDEX_OCCUPIED = 10
OBIMP_TP_STATUS_INDEX_DO_NOT_DISTURB = 11
OBIMP_TP_STATUS_INDEX_LUNCH = 12
OBIMP_TP_STATUS_INDEX_AT_HOME = 13
OBIMP_TP_STATUS_INDEX_AT_WORK = 14
OBIMP_TP_STATUS_INDEX_FREE_FOR_CHAT = 15

PNG файл дополнительных картинок статуса может существовать, если транспорт поддерживает такую функцию. Индексы в этом файле напрямую зависят от количества картинок внутри этого PNG файла. Клиент отправит выбранный индекс дополнительной картинки статуса, начиная с 1. Если клиент отправит 0, это должно пониматься как удаление дополнительной картинки статуса из информации о присутствии.

PNG файл пользовательских картинок статуса может существовать, если транспорт может иметь специальные контакты, онлайн-статусы которых не входят в диапазон статусов OBIMP. Индекс пользовательской картинки статуса начинается с 1 и будет отправлен только сервером внутри BEX информации о присутствии контакта.

Следующие sTLD полей деталей добавляются, если поддерживается обновление собственных деталей:
sTLD 0x1001: Bool, никнейм
sTLD 0x1002: Bool, имя
sTLD 0x1003: Bool, фамилия
sTLD 0x1004: Bool, код страны
sTLD 0x1005: Bool, регион/штат
sTLD 0x1006: Bool, город
sTLD 0x1007: Bool, почтовый индекс
sTLD 0x1008: Bool, адрес
sTLD 0x1009: Bool, код языка
sTLD 0x100A: Bool, дополнительный код языка
sTLD 0x100B: Bool, пол
sTLD 0x100C: Bool, день рождения
sTLD 0x100D: Bool, домашняя страница
sTLD 0x100E: Bool, о себе
sTLD 0x100F: Bool, интересы
sTLD 0x1010: Bool, email
sTLD 0x1011: Bool, дополнительный email
sTLD 0x1012: Bool, домашний телефон
sTLD 0x1013: Bool, рабочий телефон
sTLD 0x1014: Bool, сотовый телефон
sTLD 0x1015: Bool, номер факса
sTLD 0x1016: Bool, компания
sTLD 0x1017: Bool, отдел/департамент
sTLD 0x1018: Bool, должность

Следующие sTLD полей поиска добавляются, если поддерживается поиск в каталоге пользователей:
sTLD 0x2001: Bool, учетная запись
sTLD 0x2002: Bool, email
sTLD 0x2003: Bool, никнейм
sTLD 0x2004: Bool, имя
sTLD 0x2005: Bool, фамилия
sTLD 0x2006: Bool, пол
sTLD 0x2007: Bool, возраст
sTLD 0x2008: Bool, код страны
sTLD 0x2009: Bool, город
sTLD 0x200A: Bool, код языка
sTLD 0x200B: Bool, интересы
sTLD 0x200C: Bool, код знака зодиака
sTLD 0x200D: Bool, только онлайн
------------------------------------------------------------------------------------------------
Подтип: 0x0003. (OBIMP_BEX_TP_SRV_ITEM_READY)
Сервер уведомляет клиента о том, что транспорт с ID элемента готов к другим командам.
Этот BEX будет отправлен сервером только после активации присутствия. Чтобы активировать транспорты, клиент должен добавить возможность CAP_TRANSPORTS в свои возможности.

Важно! Не отправляйте никакие BEX транспортов для элемента транспорта, который еще не готов, иначе сервер может отключить клиента.

wTLD 0x0001: LongWord, ID элемента транспорта

Опционально:
wTLD 0x0002: BLK, массив доступных опций (см. ниже, как его разобрать)

Разбор данных массива опций.
Он состоит из двух частей:
1. Word, флаги настроек (см. ниже)
2. Word, количество элементов опций.
3. Массив элементов опций.

Элемент опции состоит из:
Word, длина элемента опции
Word, ID опции (уникальный ID, определенный транспортом)
Byte, тип опции (см. ниже)
LongWord, флаги опции (см. ниже)
Word, длина имени опции
UTF8, имя опции
Word, длины значения опции
UTF8, значение опции

Доступные флаги настроек:
TP_SF_HIDE_SRV_PARAMS = 0x0001

Доступные типы опций:
TP_OT_BOOL = 1
TP_OT_BYTE = 2
TP_OT_WORD = 3
TP_OT_LONGWORD = 4
TP_OT_QUADWORD = 5
TP_OT_UTF8 = 6

Доступные флаги опций:
TP_OF_CHECK = 0x00000001
TP_OF_EDIT = 0x00000002
TP_OF_COMBO = 0x00000004
TP_OF_LINK = 0x00000008
TP_OF_CHANGE = 0x00010000 (заменяет сохраненное значение опции)
TP_OF_READ_ONLY = 0x00020000
TP_OF_DISABLED = 0x00040000
------------------------------------------------------------------------------------------------
Подтип: 0x0004. (OBIMP_BEX_TP_CLI_SETTINGS)
Клиент обновляет настройки транспорта.

wTLD 0x0001: LongWord, ID элемента транспорта
wTLD 0x0002: BLK, пароль в кодировке Base64 из UTF-8 (максимальная длина 1024)
wTLD 0x0003: UTF8, хост/IP сервера (максимальная длина в кодировке UTF-8 равна 1024)
wTLD 0x0004: LongWord, номер порта сервера

Опционально:
wTLD 0x0005: BLK, массив опций (массив такой же, как в BEX выше, имена опций могут иметь пустые значения)
------------------------------------------------------------------------------------------------
Подтип: 0x0005. (OBIMP_BEX_TP_SRV_SETTINGS_REPLY)
Сервер ответит wTLD 0x0001.

wTLD 0x0001: LongWord, ID элемента транспорта
wTLD 0x0002: Word, код результата обновления настроек транспорта (см. ниже)

Коды результатов обновления настроек транспорта:
TP_SET_RES_SUCCESS = 0x0000
TP_SET_RES_ERROR_WRONG_ID = 0x0001
TP_SET_RES_ERROR_NOT_FOUND = 0x0002
TP_SET_RES_ERROR_NOT_ALLOWED = 0x0003
------------------------------------------------------------------------------------------------
Подтип: 0x0006. (OBIMP_BEX_TP_CLI_MANAGE)
Клиент управляет соединением транспорта. Если транспорт не подключен, то клиент должен отправить код подключения перед отправкой любых других управляющих кодов.

wTLD 0x0001: LongWord, ID элемента транспорта
wTLD 0x0002: Word, управляющий код подключения (см. ниже)

Если клиенту удалось подключиться или изменить статус, то wTLD 0x0003 должен быть включен:
wTLD 0x0003: LongWord, поддерживаемое значение статуса присутствия OBIMP

Если поддерживаются дополнительные картинки статуса, то следующие wTLD могут быть добавлены с кодом изменения статуса и с wTLD 0x0003:
wTLD 0x0004: LongWord, ID дополнительной картинки статуса ("0" для удаления дополнительной картинки статуса)
wTLD 0x0005: UTF8, описание дополнительной картинки статуса

Управляющие коды подключения:
TP_CON_MAN_CONNECT = 0x0001
TP_CON_MAN_STATUS = 0x0002
TP_CON_MAN_DISCONNECT = 0x0003
------------------------------------------------------------------------------------------------
Подтип: 0x0007. (OBIMP_BEX_TP_SRV_TRANSPORT_INFO)
Уведомление сервера о состоянии транспорта.

wTLD 0x0001: LongWord, ID элемента транспорта
wTLD 0x0002: Word, код состояния транспорта (см. ниже)

Коды состояния транспорта:
TP_STATE_LOGGEDIN = 0x0000
TP_STATE_LOGGEDOFF = 0x0001
TP_STATE_STATUS_CHANGED = 0x0002
TP_STATE_CON_FAILED = 0x0003
TP_STATE_ACCOUNT_INVALID = 0x0004
TP_STATE_SERVICE_TEMP_UNAVAILABLE = 0x0005
TP_STATE_WRONG_PASSWORD = 0x0006
TP_STATE_INVALID_LOGIN = 0x0007
TP_STATE_OTHER_PLACE_LOGIN = 0x0008
TP_STATE_CANT_LOGIN_TRY_LATER = 0x0009
TP_STATE_SRV_PAUSED = 0x000A
TP_STATE_SRV_RESUMED = 0x000B
TP_STATE_SRV_MIGRATED = 0x000C
------------------------------------------------------------------------------------------------
Подтип: 0x0008. (OBIMP_BEX_TP_SRV_SHOW_NOTIF)
Транспорт запросил отображение всплывающего уведомления.

wTLD 0x0001: LongWord, ID элемента транспорта
wTLD 0x0002: Bool, автоматически закрыть уведомление через несколько секунд
wTLD 0x0003: Bool, стиль уведомления об ошибке/предупреждении
wTLD 0x0004: UTF8, текст заголовка уведомления
wTLD 0x0005: UTF8, текст содержания уведомления
------------------------------------------------------------------------------------------------
Подтип: 0x0009. (OBIMP_BEX_TP_SRV_OWN_AVATAR_HASH)
Транспорт уведомляет клиента о хеше аватара собственной учетной записи.

wTLD 0x0001: LongWord, ID элемента транспорта
wTLD 0x0002: OctaWord, MD5 хеш аватара
------------------------------------------------------------------------------------------------

**********************************************************************************
3. Последовательности пакетов OBIMP

Если BEX должен быть отправлен клиентом, он будет помечен "ЗЕЛЕНЫМ" цветом.
Если BEX должен быть отправлен сервером, он будет помечен "БОРДОВЫМ" цветом.

=====================================================
3.1 Последовательности общих типов BEX
=====================================================
3.1.1 Регистрация новой учетной записи:

- Клиент подключается к серверу OBIMP

- OBIMP_BEX_COM_CLI_HELLO
     wTLD 0x0003: пустой, просто идентифицирует попытку регистрации

- OBIMP_BEX_COM_SRV_HELLO
     wTLD 0x0005: Bool, если значение True, то регистрация включена
     Опционально: wTLD 0x0006: UTF8, URL регистрации

a) Если регистрация включена
- OBIMP_BEX_COM_CLI_REGISTER
     wTLD 0x0001: UTF8, имя учетной записи (максимальная длина в кодировке UTF-8 зависит от настроек сервера)
     wTLD 0x0002: UTF8, пароль (максимальная длина в кодировке UTF-8 равна 1024)
     wTLD 0x0003: UTF8, защищенный email (максимальная длина в кодировке UTF-8 равна 1024)
     Опционально: wTLD 0x0004: BLK, текущий административный ключ сервера

- OBIMP_BEX_COM_SRV_REGISTER_REPLY
     wTLD 0x0001: Word, код результата регистрации
     Опционально:
     wTLD 0x0002: UTF8, разрешенные символы в имени учетной записи для регистрации
     wTLD 0x0003: UTF8, запрещенные первые символы в имени учетной записи для регистрации
     wTLD 0x0004: UTF8, запрещенные последние символы в имени учетной записи для регистрации
     wTLD 0x0005: LongWord, минимальная длина имени учетной записи для регистрации

- Клиент отключается

b) Если регистрация отключена
- Клиент отключается
- Если URL регистрации доступен, клиент должен предложить пользователю зарегистрироваться, используя этот URL
------------------------------------------------------------------------------------------------
3.1.2 Вход в систему:

--------------------------------------------------
Сценарий 1 (Ошибка приветствия).
- Клиент подключается к серверу OBIMP

- OBIMP_BEX_COM_CLI_HELLO
     wTLD 0x0001: UTF8, имя учетной записи

- OBIMP_BEX_COM_SRV_HELLO
     wTLD 0x0001: Word, ошибка приветствия (HELLO_ERROR_CODE)

- Клиент отключается
--------------------------------------------------
Сценарий 2 (Перенаправление сервера).
- Клиент подключается к серверу OBIMP

- OBIMP_BEX_COM_CLI_HELLO
     wTLD 0x0001: UTF8, имя учетной записи

- OBIMP_BEX_COM_SRV_HELLO
     wTLD 0x0003: UTF8, перенаправление, новый хост/ip сервера
     wTLD 0x0004: LongWord, перенаправление, новый номер порта сервера

- Клиент отключается

- Клиент перезапускает последовательность входа с начала, используя новый хост и порт сервера OBIMP
--------------------------------------------------
Сценарий 3 (Ошибка/успех/cookie входа).
- Клиент подключается к серверу OBIMP

- OBIMP_BEX_COM_CLI_HELLO
     wTLD 0x0001: UTF8, имя учетной записи

- OBIMP_BEX_COM_SRV_HELLO
     wTLD 0x0002: BLK, ключ сервера для генерации одноразового MD5 хеша пароля

- OBIMP_BEX_COM_CLI_LOGIN
     wTLD 0x0001: UTF8, имя учетной записи
     wTLD 0x0002: OctaWord, одноразовый сгенерированный MD5 хеш

- OBIMP_BEX_COM_SRV_LOGIN_REPLY
     a) wTLD 0x0001: Word, ошибка входа (LOGIN_ERROR_CODE)
         Опционально: wTLD 0x0007: UTF8, URL напоминания пароля, если код неверного пароля

     b) wTLD 0x0002: массив Word, поддерживаемые сервером BEX
         wTLD 0x0003: LongWord, максимальная длина данных клиентских BEX

     c) wTLD 0x0004: UTF8, новый хост/ip сервера
         wTLD 0x0005: LongWord, новый номер порта сервера
         wTLD 0x0006: BLK, уникальная серверная cookie

a) Если ошибка входа
- Клиент отключается
- Если URL напоминания пароля доступен, клиент должен показать его пользователю

b) Успешный вход (см. "Действия после входа")

c) Получены новый хост сервера, номер порта и уникальная cookie
- Клиент отключается
- Клиент перезапускает последовательность входа с начала, используя новый хост сервера, порт и cookie (см. сценарий "Вход с cookie")
--------------------------------------------------
Сценарий 4 (Вход с паролем открытым текстом).
- Клиент подключается к серверу OBIMP

- OBIMP_BEX_COM_CLI_HELLO
     wTLD 0x0001: UTF8, имя учетной записи

- OBIMP_BEX_COM_SRV_HELLO
     wTLD 0x0007: пустой, сервер требует аутентификацию паролем открытым текстом

- OBIMP_BEX_COM_CLI_LOGIN
     wTLD 0x0001: UTF8, имя учетной записи
     wTLD 0x0003: UTF8, пароль открытым текстом

- OBIMP_BEX_COM_SRV_LOGIN_REPLY
(следующие данные такие же, как в сценарии 3)
...
--------------------------------------------------
Сценарий 5 (Вход с cookie).
- Клиент подключается к серверу OBIMP

- OBIMP_BEX_COM_CLI_HELLO
     wTLD 0x0001: UTF8, имя учетной записи
     wTLD 0x0002: BLK, уникальная серверная cookie

a) Если имя учетной записи и cookie не совпали
- OBIMP_BEX_COM_SRV_HELLO
     wTLD 0x0001: Word, ошибка приветствия (HELLO_ERROR_CODE)

- Клиент отключается

b) Если имя учетной записи и cookie совпали
- OBIMP_BEX_COM_SRV_LOGIN_REPLY
     wTLD 0x0002: массив Word, поддерживаемые сервером BEX
     wTLD 0x0003: LongWord, максимальная длина данных клиентских BEX

- Успешный вход (см. "Действия после входа")
------------------------------------------------------------------------------------------------
3.1.3 Действия после входа:

После успешного входа клиент должен запросить параметры всех типов BEX сервера,
потому что они могут измениться, пока клиент был в автономном режиме. Поддерживаемые сервером BEX были
отправлены клиенту внутри OBIMP_BEX_COM_SRV_LOGIN_REPLY.

1. Запросить параметры для всех поддерживаемых сервером типов BEX по одному, исключая
тип OBIMP_BEX_COM, так как это базовый тип BEX:
- OBIMP_BEX_[SERVER_SUPPORTED_BEX_TYPE]_CLI_PARAMS

Например:
- OBIMP_BEX_CL_CLI_PARAMS
- OBIMP_BEX_PRES_CLI_PARAMS
- OBIMP_BEX_IM_CLI_PARAMS
- OBIMP_BEX_UD_CLI_PARAMS
- OBIMP_BEX_UA_CLI_PARAMS
- OBIMP_BEX_FT_CLI_PARAMS
- OBIMP_BEX_TP_CLI_PARAMS

2. Клиент должен запросить информацию о присутствии по умолчанию, чтобы понять, какие поля
необходимо установить или изменить.
- OBIMP_BEX_PRES_CLI_REQ_PRES_INFO

3. Запросить список контактов на стороне сервера или проверить существующую локальную копию с копией сервера.

a) Если нет локальной копии списка контактов на стороне сервера, запросить его с сервера:
- OBIMP_BEX_CL_CLI_REQUEST
- OBIMP_BEX_CL_SRV_REPLY

b) Если есть локальная копия списка контактов на стороне сервера, проверить BLOB-объект списка контактов,
вычислив его MD5 хеш и сравнив с MD5 хешем, отправленным сервером в ответе:
- OBIMP_BEX_CL_CLI_VERIFY
- OBIMP_BEX_CL_SRV_VERIFY_REPLY

4. Продолжить только после успешного получения или проверки списка контактов на стороне сервера.
Прежде чем уведомлять контакты об информации о присутствии клиента, клиент должен установить свои собственные возможности и
информацию о присутствии. Клиент всегда может изменить эту информацию во время сеанса.
После установки информации о присутствии клиент должен установить свой собственный статус присутствия.
- OBIMP_BEX_PRES_CLI_SET_PRES_INFO
- OBIMP_BEX_PRES_CLI_SET_STATUS

5. Наконец, активировать широковещательную рассылку статуса присутствия. Теперь клиент готов к обмену сообщениями.
- OBIMP_BEX_PRES_CLI_ACTIVATE

6. Запросить детали учетной записи клиента, если необходимо:
- OBIMP_BEX_UD_CLI_DETAILS_REQ
------------------------------------------------------------------------------------------------
3.1.4 Запрос автономных сообщений:

Автономные сообщения могут быть запрошены после отправки OBIMP_BEX_PRES_CLI_ACTIVATE.
OBIMP_BEX_IM_CLI_PARAMS имеет wTLD количества автономных сообщений. Если есть автономные
сообщения, запросить их:
- OBIMP_BEX_IM_CLI_REQ_OFFLINE

Сервер отправит все доступные автономные сообщения одно за другим, помеченные wTLD
автономного сообщения:
- OBIMP_BEX_IM_SRV_MESSAGE

После отправки всех автономных сообщений сервер уведомит клиента следующим BEX:
- OBIMP_BEX_IM_SRV_DONE_OFFLINE

Если клиент получил все автономные сообщения, то он должен запросить удаление автономных
сообщений, иначе сервер отправит их при следующем запросе:
- OBIMP_BEX_IM_CLI_DEL_OFFLINE
------------------------------------------------------------------------------------------------
3.1.5 Запрос автономных запросов авторизации, ответов, отзывов:

Автономные авторизационные сообщения могут быть запрошены после отправки
OBIMP_BEX_PRES_CLI_ACTIVATE. OBIMP_BEX_CL_CLI_PARAMS имеет wTLD количества автономных
авторизационных сообщений. Если есть автономные авторизационные сообщения, запросить их:
- OBIMP_BEX_CL_CLI_REQ_OFFAUTH

Сервер отправит все доступные автономные авторизационные сообщения одно за другим, помеченные
wTLD автономного авторизационного сообщения:
- OBIMP_BEX_CL_CLI_SRV_AUTH_REQUEST
или
- OBIMP_BEX_CL_CLI_SRV_AUTH_REPLY
или
- OBIMP_BEX_CL_CLI_SRV_AUTH_REVOKE

После отправки всех автономных авторизационных сообщений сервер уведомит клиента
следующим BEX:
- OBIMP_BEX_CL_SRV_DONE_OFFAUTH

Если клиент получил все автономные авторизационные сообщения, то он должен запросить удаление автономных
авторизационных сообщений, иначе сервер отправит их при следующем запросе:
- OBIMP_BEX_CL_CLI_DEL_OFFAUTH
------------------------------------------------------------------------------------------------
3.1.6 Прямая/проксируемая передача файлов:

Последовательность BEX прямого соединения и проксируемого соединения одинакова, разница только
в проксируемом соединении в том, что оба клиента должны подключиться к прокси-серверу файлов.
После установления соединения с удаленным клиентом или с прокси-сервером файлов клиент
должен отправить приветственный BEX и ждать ответного приветственного BEX от удаленного клиента:
- OBIMP_BEX_FT_DIR_PROX_HELLO

В случае сценария проксируемого соединения прокси-сервер файлов запомнит, что один
из клиентов подключился и уже отправил приветственный BEX, и прокси будет ждать второго
клиента, и после подключения второго клиента прокси отправит сохраненный приветственный BEX
от первого подключившегося клиента вновь подключившемуся второму клиенту:
- OBIMP_BEX_FT_DIR_PROX_HELLO

После получения ответа приветствия, клиент-отправитель файла должен отправить следующий BEX с
параметрами файла:
- OBIMP_BEX_FT_DIR_PROX_FILE

Если получатель готов получить этот файл, то клиент-получатель должен ответить
следующим BEX:
- OBIMP_BEX_FT_DIR_PROX_FILE_REPLY

После BEX ответа на файл, отправитель должен начать отправку частей файла, начиная с позиции
возобновления, которая была установлена в BEX ответа на файл:
- OBIMP_BEX_FT_DIR_PROX_FILE_DATA

Если есть только один файл и все части файла были отправлены, клиенты отключаются.

Если файлов больше одного, то каждый следующий файл должен быть отправлен, начиная с BEX
параметров файла и ожидания BEX ответа на файл от получателя:
- OBIMP_BEX_FT_DIR_PROX_FILE
- OBIMP_BEX_FT_DIR_PROX_FILE_REPLY

После того как все файлы и части файлов были отправлены и получены, клиенты отключаются.
